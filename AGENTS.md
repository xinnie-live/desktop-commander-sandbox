# Development Rules

[English](AGENTS.md) | [简体中文](AGENTS.zh-CN.md)

For user-requested host installation, follow [Installation with a local agent](docs/USAGE.md#installation-with-a-local-agent), including platform prerequisites and manual first-time pairing.

These rules apply to code changes and automated tests. See the [README](README.md) for supported behavior and [Contributing](CONTRIBUTING.md) for validation.

- Develop only fixed-function local CLI and on-demand Web console features. Do not add a resident daemon, startup-at-login behavior, general Docker management API, or remote control endpoint.
- Bind the local console only to `127.0.0.1`; generate a fresh local session token on every start; validate Host/Origin; disable CORS; set strict CSP. Browser APIs must not accept user-supplied commands, Compose files, paths, or project names. One fixed API without a path parameter may open the operating system’s native folder picker. The local process alone reads the selected absolute path; later browser requests may submit only a short-lived selection ID and permission options.
- Allow users to add mounts individually, up to 8 extra mounts; choose read-only or read/write for each and stage them in a list. Require one final confirmation to apply all changes. A running service may stop/restart at most once. The control process writes validated paths to per-user configuration and generates a protected Compose override at a fixed project-root path. The override is generated by the control process; never accept Compose content or mount paths from the browser. Do not place project source, local mount configuration, or control files in an Agent-writable mount; reject read/write selections that include them. Do not change permissions on user-selected folders automatically.
- Management operations may invoke only pre-listed `docker compose` operations from the fixed project root and the application-generated fixed Compose override. Read-only resource inspection is limited to `docker stats --no-stream --format '{{json .}}'` for the validated `remote-device` ID returned by the fixed Compose project, plus two fixed `docker compose exec --no-TTY --user` calls that run `du -s -B1` as UID 10001 on `/var/lib/remote-device` and UID 10002 on `/home/tool`. Never accept IDs, services, users, commands, or paths from the browser for these operations. Do not concatenate shell commands. Stop only stops containers; it does not delete named volumes. On console exit, close child processes and clear in-memory temporary output.
- The local control process uses Docker CLI/daemon permissions already held by the current OS user and must be treated as a high-privilege host control plane. Do not expose Docker Socket, host PID/network namespaces, or equivalent host-management interfaces to the Agent container.
- The product is one cross-platform Remote Device container for macOS/Windows/Linux using Docker’s default bridge. Do not add a proxy sidecar or host networking, or treat bridge networking as an outbound access-control boundary.
- Do not assume users have Clash or another proxy application. Direct container egress is the default. If needed, provide only generic, explicit, optional HTTP(S) configuration; do not hardcode ports or user environments.
- Do not start Remote Device, perform OAuth/device pairing, or connect to cloud services without the user’s explicit authorization. The user must manually verify and approve first-time pairing on the official page; never approve automatically. The local run-log feature intentionally preserves complete container stdout/stderr as described in the user guide.
- Use synthetic data and dedicated trial folders only. Do not access other real user files or existing credentials. During interactive acceptance, an agent may operate the native picker to select dedicated trial folders. The user selects other host folders. Automated regression tests must use temporary synthetic folders and must not invoke the system picker or read real folders selected by a user.
- Do not weaken security configuration to make a test pass. Prohibit `privileged: true`, broad host mounts, and unnecessary capabilities. Do not put this project’s source, authorization configuration, or control code in an Agent-writable mount.
- Do not write secrets into source code or reports. Per-run host log files intentionally preserve complete container stdout/stderr, which may include authorization links/codes, credentials, tool arguments/results, and user data. Keep these files local, apply the documented 7-file and 10 MB caps, and do not publish real logs. This does not change the requirement that the user manually approves pairing.
- Do not mark a test passed unless it was actually run and evidence was recorded. Keep unresolved items open. Avoid broad claims that the system is “secure”; state the exact property, environment, and uncovered risks.
- Pin dependencies; do not use `@latest` in place of reproducible version locks.
